## B-001 / ADR-026 (2026-10-11)

- **The app role cannot write a learner-scoped row.** P1.10's 12 integration tests are green while `persist()` cannot store anything under the role the code runs as, because the suite connects as the table **owner** and an owner is exempt from its own policies (`relforcerowsecurity = false`). `SET ROLE its_platform_app` reproduces the rejection end-to-end through `persist()`: `new row violates row-level security policy for table "diagnostic_results"`. With `SET LOCAL`/`set_config(…, true)` in the transaction the *same* run gets past RLS and fails only at `diagnostic_responses_item_id_fkey` — exactly where the owner path fails, which is what proves the GUC is the whole difference.
- **The GUC's lifecycle (PGlite 0.5.8 and PostgreSQL 15.17, identical; re-confirmed on 16.14):** `NULL` on a session that never set it; `'<uuid>'` inside the transaction that sets it; **`''`** — not `NULL` — after COMMIT and after ROLLBACK; `set_config(…, false)` **survives** COMMIT (a pooled-connection leak). So `''::uuid` raises `invalid input syntax for type uuid: ""`, and ADR-019's "unset ⇒ NULL ⇒ fail-closed" holds only on a virgin connection.
- **ADR-026 decisions:** `PgSessionContext.withLearner()` is the single writer (`set_config('app.current_learner_id', $1, true)`, bind parameter — no interpolation); transaction scope only; the predicate becomes `nullif(current_setting('app.current_learner_id', true), '')::uuid` (verified positive: own-context insert commits, other learner's is refused); a `scripts/rls-context-check.mjs` gate makes "single writer" enforceable; `migration-check.mjs` gains an assertion on the predicate **text** because counting 45 policies cannot see it.
- **Implemented and measured (2026-10-11).** `src/infrastructure/persistence/pg-session-context.ts` (single writer; blank id refused before a connection opens); the `nullif` predicate in the `learner_isolation` loop; `DiagnosticResultService.persistRun` now goes through `withLearner`, so the production path *is* the tested path; `migration-check.mjs` asserts `nullif` on `qual` **and** `with_check` of all 15 policies (`NULLIF` uppercase on deparse — the check is case-insensitive for that reason); `rls-context-check.mjs` (Rules 1–3) wired into `package.json` (`rls:check`), `test-all.mjs` and a new `rls-context` CI job that is in both `needs` lists and the fail-if condition. `tests/helpers/db.ts` gained a `TEST_DATABASE_URL` mode (real `DataSource`, drops/recreates schema `public` per caller) while the default stays PGlite; the `rls-integration` CI job runs the app-role spec on the `postgres:16-alpine` service. Evidence: the spec is **18/18 on PGlite and 18/18 on real PostgreSQL 16.14**; `migration-check.mjs` is **15 passed / 0 failed** on PG 16 (fresh cluster) including the new predicate assertion and the cross-learner `SET LOCAL` isolation check; the whole suite is **246 passed / 5 failed / 251** (the 5 still only `next-activity-selector`, ADR-021); `verify-integrity` PASS (0 fail, 1 warn), `prd-score` 96.1%. The new negative control was watched failing (owner role in place of `SET ROLE its_platform_app` → `Received promise resolved instead of rejected`) and the file restored byte-identically — that failure *is* B-001, and it is why the old 12 tests were vacuous.
- **Two things to know before running the integration suite against a real PostgreSQL you have used before.** (1) `migration-check.mjs` is **not idempotent for roles**: `CREATE ROLE its_platform_app|admin|worker` has no `IF NOT EXISTS`/`DO` guard, roles are cluster-scoped and survive `DROP SCHEMA`, so a second run in one cluster aborts at that statement and everything after it — including the RLS loop — never runs, leaving `33 tables, 0 policies` and a confusing failure. On a fresh cluster it is 15/15. CI is fine (fresh service); locally, `DROP ROLE` the three roles before re-running. (2) The harness tolerates that error by design; it does not fix the migration.
