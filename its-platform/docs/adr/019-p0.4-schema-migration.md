## Context

P0.3 ported ERD v1.0.0 §6 table-for-table into 33 TypeORM entities + 9 pure domain aggregates
+ 9 bidirectional mappers. Those entities are metadata — nothing exists in a database yet.
P0.4 must turn the ERD's DDL into a real schema, verified on **both** a local surrogate and a
real PostgreSQL 16 instance, with every §9 RLS policy, the four named enum types §11 permits,
the `[db]`-marked invariants (I-3, D-5, G-8), and the CONSTITUTION §4.6 WORM hash chain.

Three load-bearing constraints shape the design:

1. **ADR-014** forbids proving RLS on PGlite — `SET LOCAL`/role/GUC switching is only
   faithfully exercised by a real PostgreSQL server.
2. **The ERD is the single source of truth.** TypeORM's `synchronize` is off (ADR-014); a
   hand-written migration must not silently drift from the ERD. The cleanest guarantee is to
   have exactly one DDL artefact consumed by both the TypeORM migration class and the
   verification script.
3. **`verify-release-gates.py` and the CI job names are called out in BACKLOG P0.4** as the
   gate for this work (job `rls-integration`, gate `scripts/migration-check.mjs`).

## Decision

**One DDL artefact, two consumers.** `src/migrations/1791331200000-create-schema.ts` exports
`SCHEMA_STATEMENTS: string[]` — the full create-schema DDL as an ordered array of statements.
The `CreateSchema1791331200000 implements MigrationInterface` class is a thin replay
(`for (const s of SCHEMA_STATEMENTS) await queryRunner.query(s)`). `scripts/migration-check.mjs`
imports the same array from `dist/` and replays it on PGlite (default) or on real PostgreSQL
(when `DATABASE_URL` is set). Drift between migration and verification is impossible by
construction — it is the same array.

### 1. Four named enum types (§11: "four §7 vocabularies materialise as named enum types")

| Named type | Column | §7 vocabulary |
|---|---|---|
| `its_event_type` | `append_only_events.event_type` | closed 12-value event vocabulary (CONSTITUTION §4.6 owns extension) |
| `its_item_lifecycle_state` | `items.lifecycle_state` | assessment §7 lifecycle (10 values) |
| `its_fsrs_review_state` | `fsrs_states.state` | stats §6.1 review state (4 values) |
| `its_pack_layer` | `practice_attempts.pack_layer` | post-lesson §1 layer (3 values) |

Entities keep `varchar` metadata for these columns. With `synchronize: false` TypeORM never
diffs column types; enum labels round-trip as text through the driver. The DB type is the
hard gate; the entity type is a transport. Choosing **these four** over the other §7
candidates (`dialogues.status`, `modules.track`, check-backed lists): the event vocabulary is
governance-owned (extension only by amendment), the item lifecycle and review-state feed
domain switch statements, and `pack_layer` drives the L1/L2/L3 discriminator in delivery.

### 2. `[db]` invariants as triggers

- **I-3 distinctness** (`fn_item_options_distinct` / `trg_item_options_distinct`, BEFORE
  INSERT OR UPDATE OF option_text): rejects a duplicate option text after bold-marker
  normalization (`[*]+ → *`) on the same item. The full I-3 (exactly 4 options, exactly one
  key, textual degeneracy rules) stays `[domain]`; the partial unique index
  `uq_item_options_one_key ... WHERE is_key` carries the one-key half.
- **D-5 two speakers** (`fn_dialogue_min_two_speakers` / `trg_dialogue_min_two_speakers`):
  a **deferred** constraint trigger (`DEFERRABLE INITIALLY DEFERRED`) because the invariant
  is cross-row — both speakers are often inserted in one transaction. Checked at commit.
- **G-8 discriminator** (`fn_diagnostic_skill_theta_state`): BEFORE INSERT OR UPDATE OF
  skill_theta — every `{"skill": {...}}` entry must carry
  `state ∈ point_estimate | band | insufficient_evidence`.
- **WORM hash chain** (`fn_append_only_hash_chain` / `trg_append_only_hash_chain`, BEFORE
  INSERT): computes `prev_hash` = last row's `row_hash` and `row_hash = sha256(serialized
  row)`. Serialization with `pg_advisory_xact_lock('its_platform_append_only_chain')`
  serializes concurrent appends so the chain cannot fork — this is the mechanism P2.2
  proves under concurrency. `sha256` is core (no pgcrypto extension needed), so the migration
  is extension-free and replays identically on PGlite.

### 3. RLS §9 on real PostgreSQL

One DO block loops the 15 `(table, predicate)` pairs — `learners` uses `id`, all others
`learner_id` — executing ADR-003's template: `ENABLE ROW LEVEL SECURITY`, then
`learner_isolation` (USING + WITH CHECK, FOR ALL TO `its_platform_app`),
`admin_bypass` (USING true, TO `its_platform_admin`), `worker_access` (USING true, TO
`its_platform_worker`). Roles are created NOLOGIN.

**Implementation note (deliberate refinement):** the predicate uses
`current_setting('app.current_learner_id', true)::uuid` — the **missing_ok** variant —
where the ERD template shows the strict two-argument form. An unset GUC then evaluates
NULL: SELECT sees nothing, INSERT is rejected (fail-closed). The strict form would raise a
hard "unrecognized configuration parameter" error on any session that forgot `SET LOCAL`,
breaking migrations and tooling; fail-closed NULL is the same security posture with better
operability. Behaviour is asserted on real PostgreSQL (isolation, X-3, I-2 column grants).

Grants: `its_platform_app` and `its_platform_worker` receive DML **minus** the WORM tables
(`append_only_events`, `consent_records`: no UPDATE/DELETE — X-1/X-3), minus `DELETE` and
`UPDATE (id)` on `items` (I-2 identifiers immutable); `its_platform_admin` receives ALL.
BLANKET grant first, then REVOKEs — order is explicit in the statement array.

### 4. CI job `rls-integration`

A dedicated GitHub Actions job with `services: postgres:16-alpine` runs
`npm ci` → `npm run build` → `DATABASE_URL=... node scripts/migration-check.mjs`, and is
added to the `summary` aggregate. This is the ADR-014 real-PostgreSQL verification: RLS
isolation via `SET ROLE its_platform_app` + `SET LOCAL app.current_learner_id`, X-3 WORM
grant denial, I-2 column-grant denial — each executed as the `its_platform_app` role.

## Consequences

### Positive

- One DDL artefact consumed by migration **and** gate — ERD drift surfaces as a migration-check
  failure, not as a production surprise.
- RLS, WORM grants, enum types and the hash chain are now *proven* on PostgreSQL 16 in CI,
  closing the ADR-014 gap and the §9 (correction 16) verification debt.
- Extension-free DDL replays byte-identical on PGlite and PostgreSQL.
- Deferred D-5 trigger matches the cross-row reality of dialogue authorship.

### Negative

- The four enum types live **only** in the DB; entities carry varchar. A future
  `migration:generate` run against an empty DB would regenerate the schema with varchar
  CHECKs instead of named enums — the hand-written migration must stay authoritative,
  P0.4 has documented this.
- `pg_advisory_xact_lock` serializes appends to `append_only_events`; throughput is
  bounded by chain-write latency (acceptable: the ledger is append-mostly; P2.2 measures).
- The DO block generates policies dynamically — `grep CREATE POLICY` against the migration
  finds the template, not 45 literal statements (pg_policies is the authority; the gate
  asserts 45).

### Neutral

- `down()` reverses: policies → tables (CASCADE) → enum types → roles.
- Script chooses backends by env: no `DATABASE_URL` => PGlite; set => real PostgreSQL.
- The hash chain guarantees **sequential appends** (one INSERT per event — the app's write
  pattern, and how the gate tests it). A multi-row INSERT cannot chain: row triggers do not
  see sibling rows of the same statement, so rows 2..n would each read the pre-statement
  tail. Bulk writers must append row-at-a-time or prove a batch strategy under P2.2.

## Alternatives Considered

1. **TypeORM `synchronize: true` for P0.4** — rejected: cannot express enums, triggers,
   policies or grants; would drift from the ERD immediately.
2. **Two DDL artefacts (migration SQL + standalone verification SQL)** — rejected: drift
   risk between them is exactly the class of error this repo's gates exist to catch; one
   array costs nothing.
3. **PGlite-only verification** — rejected: ADR-014 explicitly forbids proving RLS there.
4. **Strict `current_setting()` in policies** — rejected: hard error on unset GUC breaks
   migrations and tooling, with no security gain over fail-closed NULL.
5. **No deferred trigger; application-layer D-5 only** — rejected: D-5 is marked `[db]`
   in the domain model and the ERD §10 table schedules it in P0.4.
